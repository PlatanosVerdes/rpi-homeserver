# 2026-09-20 - aceserve: dnsproxyd drops concurrent queries

## What changed (streamhalla, rpi-homeserver/compose-media.yml)
1. New config/aceserve/dnsproxyd.py, mounted over /acestream/dnsproxyd.py
   (:ro). Against the image's own file:
   - listen(1) -> listen(128)
   - queries answered inside the accept loop -> ThreadPoolExecutor(32)
   - a stale /dev/socket/dnsproxyd is unlinked before bind
   Wire protocol, response structs and the dns_daemon() entry point are
   unchanged, so main.py keeps importing it the same way.

## Why
The engine runs on an Android runtime, whose resolver does not read
/etc/resolv.conf: it queries /dev/socket/dnsproxyd, and main.py serves that
socket from this module. The image answered one connection at a time, so the
engine's concurrent lookups were refused outright and surfaced as
getaddrinfo EAI_NONAME.

Measured against the live socket, 100 queries 4 at a time:
  before  75 OK / 25 BlockingIOError  (25% lost)
  after  100 OK / 0                   (0% lost)
  after, 16 at a time: 160/160

The loss matters most when the engine is already degraded. On 2026-09-19 the
AceStream bootstrap IPs were blocked upstream, netmon retried without pause
and the log took ~3700 'check_connection: failed' per hour. With the
bootstrap reachable it is 4 per boot.

## Trade-off / notes
- Bounded at 32 workers: a burst past that queues rather than failing.
- Still IPv4 only (AF_INET), same as the image. The 4 failures ~6s into every
  boot are the engine's IPv6 probes: this box has no IPv6 (media-network
  EnableIPv6=false), the same limitation already noted in
  CHANGES-2026-08-31. They stop once netmon settles on connected.
- The mount survives image updates, so the fix does not depend on
  jopsis/aceserve:latest keeping this file as it is. If the image ever stops
  importing dnsproxyd, the mount is inert, not harmful.

## Revert (fully)
  cd ~/rpi-homeserver
  cp .backups/20260920-215241/compose-media.yml compose-media.yml
  rm config/aceserve/dnsproxyd.py
  sudo docker compose up -d aceserve


# 2026-09-20 - bootstrap reachability metric + panels

## What changed
1. scripts/acestream-updater/script.sh: check_bootstrap() opens and closes a
   TCP connection to each address in BOOTSTRAP_ADDRS and pushes
   acestream_bootstrap_reachable{addr} (1/0) in the existing push to
   job/acestream_updater. Runs once per cycle, before the downloads, so both
   push paths carry it.
2. config/grafana/dashboards_json/acestream.json: two panels,
   'Bootstrap Reachability' (state-timeline, id 10) and
   'Blocked Time (24h)' (stat, id 11).

## Why
When those peers are unreachable no channel plays and the stack looks broken:
aceserve answers 500 'failed to load content' for every id, and Jellyfin
reports FFmpeg errors. Telling that apart from a real stack fault took a full
session on 2026-09-19. The panel answers it at a glance, and the history
shows whether the blocking is windowed or permanent.

## Trade-off / notes
- Cost per cycle, measured in the container: 0.104s wall, 0.011s CPU, 0 bytes
  transferred. The m3u download the same cycle already does is 0.020s.
  Nothing touches aceserve: no engine session is opened, so none is left open.
- Worst case with the peers blocked, the two timeouts idle for up to 10s.
  It is wait, not load.
- The addresses are hardcoded because the engine dials these two. They were
  read off its sockets; if it ever dials others the metric silently measures
  the wrong thing, so re-check BOOTSTRAP_ADDRS against
  'nsenter -t <aceserve pid> -n ss -tn' before trusting a flat line.
- No alert: a blocked peer is not something this box can act on.

## Revert (fully)

  cp .backups/20260920-215241/script.sh scripts/acestream-updater/script.sh
  cp .backups/20260920-215241/acestream.json \
     config/grafana/dashboards_json/acestream.json
  curl -X DELETE http://127.0.0.1:9091/metrics/job/acestream_updater
